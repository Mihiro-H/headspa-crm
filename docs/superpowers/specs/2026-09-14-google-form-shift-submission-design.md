# Googleフォームによるシフト希望提出フロー 設計書

- 日付: 2026-09-14
- 対象: スタッフシフト管理機能（既存: `docs/superpowers/specs/2026-09-13-staff-shift-management-design.md`、`docs/superpowers/specs/2026-09-13-shift-request-type-redesign-design.md`）に、Googleフォーム経由の提出経路を追加する
- 位置づけ: 管理画面(`/admin/my-shift-requests`)からの入力は維持したまま、Googleフォームを**もう一つの入力経路**として追加する。以降のフロー（AI自動生成→店長確定）は変更しない。

## 背景・目的

現状、スタッフは管理画面にログインして希望を入力する必要がある。これに加えて、Googleフォームからも提出できるようにし、スタッフの提出手段の選択肢を広げる。

## 全体フロー

```
スタッフがGoogleフォーム提出
  → Google Apps Script（フォームに設定、本設計書のコードを貼り付け）が自動起動
  → アプリの新規APIエンドポイント（/api/shift-form-webhook）にPOST
    （Bearerトークン認証、既存の /api/cron/[jobName] と同じ方式）
  → 該当スタッフ・該当月の既存のStaffShiftRequestを全て削除
  → フォーム回答の内容を新規にStaffShiftRequestとして反映
```

## フォーム構成

Googleフォーム自体はユーザー側で作成する（本設計書はその質問構成とApps Scriptコードを提供する）。

1. **対象年月**（プルダウン、例: `2026-10`）。「いつ出しても来月分」のような曖昧な自動判定はせず、毎回明示的に選んでもらう。
2. **お名前**（プルダウン、`店舗名 - 氏名`形式。例: `渋谷店 - 松本陸`、`新宿店 - 松本陸`）。同姓同名（兼任スタッフ等）を区別するため店舗名を必ず併記する。
3. **休み希望の日**（日付の複数選択）
4. **時短希望の日と時間**（自由記述、1行1件。書式は「日付 開始-終了」または「日付 開店〜終了」「日付 開始〜閉店」。例:
   ```
   10/5 11:00-15:00
   10/12 開店〜14:00
   ```
   ）

未回答の日は全て「出勤（店舗営業時間フル）」として扱う（既存の`deriveDraftShift`の「未提出＝出勤扱い」ルールと同じ考え方を、フォーム上でも「書かなければ出勤」という形で踏襲する）。

### スタッフ一覧プルダウンの運用

質問2のプルダウン選択肢は、店舗異動・入退職のたびに手動更新が必要。`/admin/staff-shifts`に「フォーム用スタッフ一覧をコピー」ボタンを追加し、対象店舗のアクティブなスタッフを`店舗名 - 氏名`形式で1行ずつ、クリップボードにコピーできるようにする。管理者はこれをGoogleフォームの選択肢欄に貼り付ける。

## データモデル・突合ロジック

新規テーブルは不要。既存の`StaffShiftRequest`（`staffId`/`workDate`/`requestType`/`preferredStartTime`/`preferredEndTime`）にそのまま書き込む。

`店舗名 - 氏名`の突合は、`Staff`テーブルを`store`ごとJOINして`店舗名 - 氏名`文字列を生成し、完全一致するレコードを検索する。一致しない場合（店舗名変更・スタッフ退職などでプルダウンが古いまま送信された場合）は、その回答全体を`unmatched_staff`エラーとして扱い、`StaffShiftRequest`への書き込みは行わない。

## 時短希望の自由記述パース

1行ごとに以下を試みる:

- 日付部分: `M/D`形式（例: `10/5`）。全角数字・全角スラッシュも許容する。
- 区切り: `-`（半角ハイフン）、`〜`、`~`のいずれも許容する。
- 時刻部分: `HH:MM`形式、または`開店`（店舗の営業開始時刻）・`閉店`（店舗の営業終了時刻）というキーワード。

パースに失敗した行は**黙って無視しない**。その回答（1スタッフ・1ヶ月分）全体の処理結果に「不明な行」として記録し、Webhookのレスポンスに含める（Apps Script側の実行ログで確認できる）。不明な行があっても、パースできた他の行（休み希望日など）は正常に反映する。

## 置き換え（Upsert）の挙動

同じスタッフが同じ月に対してフォームを再提出した場合、**その月・そのスタッフの既存のStaffShiftRequestを全件削除してから、新しい回答内容を反映する**（部分マージはしない）。

**重要な注意点**: この「全件置き換え」は、そのスタッフ・その月の希望データ全体に対して行われる。つまり、`/admin/my-shift-requests`で個別に入力した内容も、後からGoogleフォームが提出されると上書きされて消える。1人のスタッフが同じ月に対してアプリとフォームを両方使った場合、後から提出された方が勝つ。

この挙動をスタッフ本人が認識できるよう、`/admin/my-shift-requests`画面に「Googleフォームからも提出されている場合、後から提出された方が優先されます」という趣旨の注意書きを追加する。

削除→挿入は`$transaction`でまとめて実行し、既存の`generateShiftDraftForStore`等と同じく、途中失敗による中途半端な状態を防ぐ。

## 新規API・認証

`app/api/shift-form-webhook/route.ts`（新規、Route Handler）。

- 認証: `Authorization: Bearer <SHIFT_FORM_WEBHOOK_SECRET>`ヘッダー。既存の`/api/cron/[jobName]/route.ts`と同じ方式（`process.env.SHIFT_FORM_WEBHOOK_SECRET`と比較）。
- リクエストボディ（Apps Scriptが送信するJSON）:
  ```json
  {
    "staffLabel": "渋谷店 - 松本陸",
    "yearMonth": "2026-10",
    "dayOffDates": ["2026-10-05", "2026-10-12"],
    "reducedFreeText": "10/5 11:00-15:00\n10/12 開店〜14:00"
  }
  ```
- レスポンス: 成功時`{status: "ok", dayOffCount, reducedCount, unparsedLines: string[]}`。`staffLabel`が突合できない場合は`{status: "unmatched_staff"}`（400）。

## Google Apps Script（ユーザーがフォームに設定するコード）

フォームの「拡張機能 > Apps Script」に貼り付け、トリガーを「フォーム送信時」に設定してもらう。設計書内にコード全文を用意し、`WEBHOOK_URL`と`WEBHOOK_SECRET`の2箇所だけ書き換えれば動く形にする。フォームの質問文と、Apps Script内の質問タイトル文字列（回答取得に使う）を完全一致させる必要がある旨も明記する。

## スコープ外（今回やらないこと）

- フォーム送信直後の確認画面への動的なフィードバック表示（Googleフォームの標準機能では不可）。パースエラー時のスタッフ本人への通知（メール等）は今回作らない。
- スタッフ一覧プルダウンの自動同期（手動コピー＆貼り付け運用）。
- Googleフォーム自体の作成（ユーザー側で行う。本設計書は質問文言とApps Scriptコードのみ提供）。

## テスト方針

- 自由記述パース関数（`lib/scheduling/parse-reduced-free-text.ts`想定）は純粋関数として切り出し、日付・時刻の書式揺れ、不正行の扱いを含めて単体テストする。
- Webhookのハンドラ（認証、スタッフ突合、全件置き換えのトランザクション）はTDDでテストする。
